# Pronark next-phase plan

Status: local implementation in progress, October 10, 2026. Navigation labels, Your Progress and owner-only standalone metrics, time-of-day checklist display, a disabled-by-default 1st/15th target-growth worker, and the focused resumable onboarding in `src/GuidedSetup.tsx` are implemented locally. The income illustration is not persisted. Later local work adds category-based companion reactions (migration 19), draft Custom reminder settings/worker (20), private multi-group membership and per-group sharing (21), visual-only Together gardens, missions, cheers, and opt-in Versus (22), plus a local-only receipt photo/manual-review flow. `npm run build` and `npm test` pass locally, including group isolation and garden-correction database tests. Migrations 19–22 have **not** been applied to the live Supabase project, nor has this version been deployed or browser-accepted across multiple accounts. Monetary garden multipliers, automatic receipt OCR, statement import, and live Custom reminder delivery remain gated; no real sends or paid calls were made. `PRD.md` remains authoritative for existing behavior. Do not silently change reward, correction, group-permission, or Google Sheets rules.

## 1. Decisions and intended experience

### Approved in conversation

- Rename the navigation label currently shown as **Rewards** (the savings/category page, internally `Goals`) to **Goals**. Rename the navigation label currently shown as **Wallet** (balance, earnings, purchases) to **Rewards**. Keep the word *wallet* inside the Rewards page for the earned balance. Update desktop sidebar, mobile navigation, headings, breadcrumbs, dialogs, help copy, and accessible names together; avoid changing database identifiers only to rename UI.
- First-time setup is a calm, guided sequence: profile and companion/preferences; build the checklist; set goals; understand wallet-versus-target-versus-assigned progress; then enter Home. Existing users retain their data and should not be forced through it.
- Build a checklist by choosing suggested activities or adding one, **customizing one activity at a time** (days, routine notes, reward, optional KPI), then reviewing/reordering the finished list. Support drag-and-drop and keyboard/Move up/down controls. Templates and the existing monthly reward/schedule locks still apply.
- Goals setup offers **self-directed** and **budget-guided** paths. Both rank spending priorities and set/edit one category or item at a time. The budget path starts its discretionary-goal slider at 15% but does not claim this is universally affordable.
- A recurring goal plan may add an amount to the **goal target** on the 1st and 15th of each month. It does **not** create earnings, add money to the wallet, or assign wallet earnings. Example: initial Jewelry target $600; +$75 on October 1 → $675; +$75 on October 15 → $750. If earned-and-assigned progress was $120, it remains $120. Specify dates rather than calling this “every two weeks” (which is a different schedule).
- A person can transfer assigned progress from a category's general pool to a specific item in that category. Example: General Jewelry $120 → move $40 → General $80, necklace $40; category total and wallet balance stay unchanged. Preserve the existing purchase/correction behavior when that item is later bought or a purchase is reversed.
- Setup and routine-use screens retain the approved Pronark visual direction: ivory/white surfaces, deep green actions, mint cards, soft rounded corners, approachable icons, generous space, and an original supportive companion. They should be **separate, focused screens**, not the densely packed composite image boards.
- Each setup section has a short, contextual, expandable FAQ, plus a way to revisit the walkthrough. Completion feedback is activity-specific and positive. A gym checkoff can make the companion flex; other activities get appropriate small animations. Let people reduce or turn off animation and companion chatter.
- A receipt/statement photo feature is desired. The recommended behavior is **scan → prefill → review → confirm purchase**, never silently post a purchase from OCR. Statement import is a later, more sensitive stage than single-receipt import.
- Replace the current one-group/two-person assumption with multiple private, invite-only groups per account. The top-level view becomes **Me | Groups**; Groups opens a group selector and then a member selector. A person sees only groups they belong to. Sharing is configured **per group**: progress summary and selected activities by default, with an explicit opt-in for that group to see full checklist/history. The existing two-person group and data must survive migration.
- Add a **Together** area for each group. Its main mode is cooperative: a shared garden containing multiple user-created plants, weekly missions, encouraging check-ins, and a recap. Each plant may track a shared checklist activity, a KPI, or another clearly defined group metric. Members may choose how many plants to create, subject to reasonable service limits for performance/abuse rather than an arbitrary product cap.
- An optional private **Versus** mode may compare consenting participants against their own plans. No public rankings, automatic enrollment, wallet/purchase visibility, or exposure of one group's data to another.
- A plant may optionally carry a cooperative reward multiplier. Garden-only is valid. Any monetary multiplier is **at most 2×**, requires explicit participant opt-in and a precisely defined qualification rule, and must not silently stack with other garden multipliers or bypass the existing negative-balance/streak-bonus protections. Exact interaction with existing bonuses is a proposed rule below, not yet a newly approved accounting formula.
- Approved October 8: for a monetary garden plant, both participants must opt in and meet their own goals. An eligible participant can earn at most 2× the base reward total, with no stacking, no bonus while their wallet is negative, and **at most $10 extra garden bonus per person per week**.
- Expand Insights with a separate **Your Progress** slide/section for numeric KPIs, apart from checklist **Consistency**. Existing activity KPIs (steps, miles, water, etc.) appear there without duplicate logging. Also allow opt-in, standalone metrics that are **not checklist activities**, such as weight or calories, with their own logging and trends.
- Approved October 8: private weight and calorie measurements are excluded from Google Sheets by default.
- Let each activity optionally be marked Morning, Afternoon, Evening/Night, or Anytime. Users can show one grouped checklist with these section headings or keep a single prioritized list. Time-of-day is an organizational cue unless a separate reminder is enabled; it does not change scheduled weekdays, checkoff eligibility, earnings, or monthly locks.
- Keep the current standard push schedule as the default. Offer owner-controlled extra reminders (general or activity-specific), quiet hours, and frequency controls, with a clear preview of expected alerts and an Off option. Extra notifications require explicit opt-in; no new real sends are authorized by this plan.

### Proposed defaults needing final product confirmation before implementation

- Ask for **take-home income** and pay frequency for budget guidance; gross income may be optional context, not the main calculator input. Store income only if the person explicitly chooses “save my budget”; otherwise calculate in-session and discard it. No bank account connection.
- A target-growth plan changes the target on the 1st/15th in the app's established America/New_York day boundary. On the start date, apply one increment per scheduled date with idempotent processing. Pausing stops future increments; it does not undo past increments. Editing the amount affects future increments, with an explicit preview.
- Receipt image files are deleted after extraction and user confirmation/cancellation by default; retain extracted purchase fields and the normal audit trail. If the user wants an image archive, make it a separate opt-in setting and define retention.
- Do not build automatic wallet allocation from the target-growth schedule. If requested later, that must be a distinct opt-in feature that assigns only available earned funds, and is never confused with target growth.
- For a multi-member group, a plant defines its participating members and whether **all** or a named pair must meet their own target in the same period. For the first monetary-multiplier release, recommend a two-person pair requirement; gardens without money multipliers can involve the whole group. Require both eligible people to accept a monetary rule before it starts; changes affect future periods only.
- Treat garden growth as visual/group progress, not a new wallet balance. Recommend that the optional multiplier adds at most one extra base-reward amount per qualifying participant and activity/date (2× total base reward), is computed once after all required checkoffs/KPIs are verified, and is reversed on correction. Do **not** multiply streak bonuses or compound multipliers. If an activity is eligible through multiple groups/plants, at most one cooperative bonus applies for that activity/date. A negative wallet still receives normal base rewards but no bonus multiplier while the existing bonus pause applies. This is the safest proposed formula; confirm it before database work.

## 2. User journey: focused screens

Use a small progress indicator, Back/Continue, Save draft, and Skip only where safe. Preserve inputs on failure. The onboarding checkpoint should be persisted per owner and version so interrupted setup resumes, and an existing account sees a non-destructive “Explore what's new” walkthrough instead of a reset.

| Screen | One main decision | Data saved / result | Contextual FAQ examples |
| --- | --- | --- | --- |
| Welcome | Start, resume, or skip guidance | Onboarding version/status only | “Will this change my current data?” |
| Profile | Name and optional personal context | Existing owner profile fields | “Who can see my profile?” “Can I edit it later?” |
| Companion | Pick robot, dog, cat, muse, or gentle helper; preview tone | Owner preference, ideally synced across devices | “Can I change companions?” “Can I turn messages off?” |
| Preferences | Reminder and companion/animation choices | Owner preferences without changing existing notification consent | “Will this send me emails?” “How do I pause reminders?” |
| Activity library | Choose one suggestion/template or “Create my own” | Draft selection only | “Are suggestions required?” “Can I add one later?” |
| Customize activity | Name, notes, weekdays, reward, optional unit/target | Create one task with existing validation/monthly locks | “Do I need a KPI?” “What happens on rest days?” |
| Checklist review | Reorder, add another, edit individual card, confirm | Owner-specific display order; **not** a new reward ordering | “Can I reorder later?” “Does order affect earnings?” |
| Goals path | Self-directed or budget-guided | Choice and draft plan | “Does this move real money?” |
| Budget inputs (optional) | Take-home amount, paycheck cadence, initial 15% slider | Draft calculation; persist only with explicit consent | “Gross or take-home?” “Twice monthly or every two weeks?” |
| Priority ranking | Rank categories/desired spending areas | Owner-specific priority order | “Does ranking limit my spending?” |
| One goal | Initial target, optional items, suggested amount, optional target-growth schedule | One category/item target and schedule, confirmed per screen | “Can my goal exceed my wallet?” “Can I pause growth?” |
| Goals review | Review all target amounts, monthly/yearly equivalents, edit | Confirmed setup; no earnings or allocations created | “What happens when I buy an item?” |
| Money explainer | Work through a **sample-only** target/wallet/assignment example | Education completion flag only | “What is assigned?” “Is this a bank account?” |
| Finish | Enter Home; offer Replay in Profile/Settings | Onboarding complete | “Where do I change this later?” |

Do not require every optional screen to be completed to use the app. Partner mode remains read-only and never runs the owner's setup editor. Onboarding must not bypass the established first-day restrictions for existing monthly rewards/settings; for a genuinely new task, use the existing creation allowance.

### Budget guidance details

- Clearly label the 15% default as an **editable starting illustration**, not financial advice or an affordability promise. Ask whether pay is twice monthly (24 payments/year), every two weeks (26), monthly, or irregular. Show per-paycheck, monthly, and yearly equivalents using the chosen cadence.
- Show the user's entered take-home income, the chosen *discretionary goal planning amount*, and the ranked-goal split as three different values. Suggested goal targets are editable, never automatically adopted. Include a reminder to account for essentials, debt, and emergency needs; do not hard-code a 30/40/20 rule as a universal recommendation.
- Self-directed setup needs no income input. There should be an obvious “Skip budget guidance” path.
- Validate negative/zero/implausible entries, rounding in cents, annual/monthly conversions, and an irregular-income explanation. Never send the income figure to Google Sheets unless the user explicitly agrees to that sensitive-data mirror; a safer default is not to persist it at all.

### Goal accounting invariant

The UI and backend must always distinguish **target** (what the person wants to save), **wallet balance** (earned minus purchases/corrections), **assigned** (how much of wallet earnings is earmarked), and **planned target growth** (future increases to target). A target may exceed the wallet or assigned amount. Target growth changes only the target. Allocation changes assigned progress but not wallet balance. A purchase changes wallet balance once, with existing linked-item accounting. Garden growth alone is not money; an optional, agreed multiplier is a distinct audited earning under the rules below. Display target progress as assigned / target, with zero-target handling and no misleading >100% cap in the stored values.

## 3. Everyday use after setup

### Companion messages and behavior

Create an activity-to-reaction mapping based on an optional semantic category/icon chosen by the user; do **not** guess from arbitrary title text alone. Default/custom activities get a general response. Examples:

| Activity | Example line | Motion cue |
| --- | --- | --- |
| Gym/strength | “You showed up for yourself today. Strong work!” | Small flex |
| Run/walk | “Every step counts. You did that!” | Two jogging/walking steps |
| Water | “A little care for yourself, one sip at a time.” | Lift a cup/drop |
| Reading | “You made room to learn today.” | Open a book |
| Morning routine | “You gave your day a thoughtful start.” | Stretch and wave |
| Other/custom | “You followed through on something that matters to you.” | Gentle bounce or wave |

Keep several lines per category and select deterministically per activity/date to avoid the same line on every render. A successful **server-confirmed** checkoff triggers at most one short celebration, never on a failed write, pending state, partner read-only view, page reload, or historical correction unless explicitly designed. If a KPI has not been met, the line cannot claim it was met. Undo should clear the completed state and show a calm correction confirmation rather than a second celebration. Do not shame missed days or negative balances; the established negative-balance/streak-bonus rules remain authoritative.

The everyday surface can show a small companion speech bubble for completion. Save full modal celebrations for meaningful milestones, with a close button, focus handling, and an option to silence future popups. Turn off confetti, large scale changes, and travel movement for reduced-motion users. The selected companion and its voice/tone should appear consistently on Home, recap, and celebrations; today only the robot has a dedicated art asset, so the other companion art/animation states require design work before promising equal visual fidelity.

### Multiple private groups and Together garden

**Navigation and scope.** Replace Me/Partner with **Me | Groups**. In Groups, select a group, then a member or the group's Together view. The selected group ID must scope every query, card, notification, URL, cache key, and export. Show a persistent group name in the header so users cannot mistake Family for their partner group. The current schema has `memberships.user_id unique`, a two-member invite limit, and a broad `app.same_group` predicate; all three must be redesigned before a second group is enabled. It is not sufficient to hide groups in the frontend. A user in both Family and Partner groups must never accidentally relay one group's private membership, challenges, notes, or activity details into the other.

**Per-group privacy.** Default sharing is an aggregate progress summary plus individually selected activities. A separate OFF-by-default permission reveals full checklist/history **to that group only**. Let users preview “What this group can see,” revoke access instantly, and keep their own records editable only by themselves. For an unshared activity used to grow a plant, show only the explicitly consented challenge contribution (for example “1 contribution”) and not the title, notes, KPI value, wallet, purchase, or other group's existence. Small groups may infer a participant's contribution from totals; disclose that on opt-in. Prevent group names, invite codes, member lists, challenges, and images from appearing in unrelated group views or Sheets exports shared beyond their intended audience.

**Garden object.** Each group has one garden with zero or more plants. A plant has a name, visual species/theme, creator, participants, growth rule, measurement window/timezone, progress, lifecycle (`draft`, `active`, `paused`, `archived`), visibility, and optional multiplier rule/version. Offer simple presets: “Our shared activity,” “Our KPI target,” “Our weekly consistency,” and “Custom metric.” A personal main plant can reflect a person's own completed scheduled checkoffs; it is private unless separately shared into a group. A group plant counts only consented contributions from its participating members. One activity may water multiple **visual** plants, but cannot generate multiple monetary bonuses for the same activity/date. Empty gardens invite the group to plant the first seed; archived plants remain in a history shelf rather than disappearing.

**Growth definitions.** The plant editor chooses one understandable rule at a time: linked activity/checkoff (each participating person completes their own selected activity), KPI target (each reaches an agreed or individualized target with a unit), or weekly aggregate metric (for example 12 scheduled checkoffs combined). Show a preview: “This plant grows when X of Y participants do Z by Sunday.” Use only server-confirmed, scheduled, eligible checkoffs/KPI logs. A participant may select a different personal activity or KPI for a shared theme; compare completion against their own target, not raw miles/steps or number of tasks. Show a contribution ledger and correct growth if records are edited/undone. Do not let a vague custom metric pay money until it has an objectively verifiable source and validation rule; it may be visual-only.

**Cooperative modes.** Weekly missions provide a shared goal and one progress bar. The garden turns mission progress into visible stages such as seed → sprout → leaves → flower, without decay or shame after a missed day. Group members can choose a longer shared build (new bed/path/constellation), send a limited set of supportive cheers, opt into buddy promises, and see a warm weekly recap. A separate Versus card is optional, private, time-limited, and includes only consenting members; it compares rate against each person's scheduled plan. No forced leaderboard. These are distinct panels within Together, not all controls packed onto one screen.

**Optional multiplier safety.** The plant creation flow offers three clear choices: “Garden only” (default), “Garden + cooperative challenge, no money bonus,” and “Garden + reward multiplier.” For the last, choose a multiplier from 1.0×–2.0× and display the maximum extra dollars per qualifying activity/person and per challenge window before anyone agrees. Both participants must affirm the rule; a group admin cannot impose a wallet effect on someone else. Base rewards remain under existing task settings and month locks; changing a plant does not retroactively edit them. Qualify and post the separate bonus only after the window closes and all required contributions are verified, with a unique qualification key, audit trail, and correction/reversal path. No multiplier on the multiplier, no cross-plant stacking, and no payout for a plant lacking an eligible base-reward activity. A 2× cap is not enough by itself to bound dollar exposure when base rewards or repeated days are large; add a disclosed per-period bonus cap and preview, to be agreed before build.

**Example.** Two people opt into a Gym plant for a week. Each has a $2 eligible base reward for their own scheduled Gym checkoff. If both complete the agreed day and the rule is 1.5×, each receives their normal $2 base reward plus a separate $1 cooperative bonus (total $3 for that activity/date); the plant grows for both. If only one finishes, the completed person retains the $2 base reward and the plant may record their contribution, but neither gets the cooperative bonus. If a checkoff is later corrected to incomplete, the corresponding cooperative bonuses are reversed once and garden progress recalculates. This example is a proposed formula, not a live payout.

**Contextual FAQs.** Group selector: “Who can see my groups?” “Can I belong to more than one?” Sharing: “Can Family see my Partner group?” “What does full history include?” Plant editor: “Does a plant change my wallet?” “Can one activity grow two plants?” Multiplier: “Who has to agree?” “When is a bonus paid?” “What happens if someone misses or corrects a day?” Versus: “Who can see the comparison?” “Can I leave?” Provide these beneath the relevant focused screen, with plain-language answers and a link to complete help.

### Insights: consistency versus measurable progress

**Information architecture.** Insights has two clearly labeled lanes: **Consistency** answers “How often did I do what I planned?” using scheduled opportunities, checkoffs, and heatmaps; **Your Progress** answers “What numbers changed?” using KPI measurements. Make them separate slides/tabs in the Insights page and separate cards in the monthly recap, not a single blended score. Examples: total/average steps with daily/weekly trend, miles run with total and per-run trend, water amount, and any standalone metric the owner created. Do not interpret a missing log as zero. Show source, unit, timeframe, number of logged days, and whether a number is a sum, average, latest value, or target attainment. Allow activity, metric, date range, weekday, and completion filters where mathematically meaningful; export both data types without changing existing consistency calculations.

**Standalone metrics.** “Add a metric” is separate from “Add an activity.” It asks for name, unit, measurement type (`count`, `distance`, `volume`, `weight`, `energy`, or custom numeric), logging cadence (daily/weekly/as needed), aggregation (sum/average/latest), and optional goal/direction. Examples: Weight (lb or kg; latest/trend, no automatic “more is better” judgment) and Calories (kcal; user-entered daily total, no food database or nutrition prescription in the first version). Entry is dated, editable, and deletable with audit/correction history. It creates **no checklist item, completion, dollars, streak, garden reward, or notification by default**. If a metric is later linked to an activity or plant, require an explicit, reviewable link and avoid logging the same measurement twice.

**Health-data guardrails.** Weight and calorie data can be sensitive. Keep them private to their owner by default, excluded from group summaries, Versus, garden feeds, push text, and shared exports unless that metric is individually opted in for a specific group and purpose. Provide Hide/Archive/Delete controls, neutral chart copy, no moral labels for increases/decreases, and no automatic calorie advice. A missed log is not a failed day. Standalone metrics should remain optional so Pronark stays a habit-and-goals app rather than becoming a prescriptive diet app. CDC notes calorie counting is not necessary for everyone, and research on weight-related self-monitoring warrants careful, user-controlled design. [CDC guidance](https://www.cdc.gov/healthy-weight-growth/about/tips-for-balancing-food-activity.html), [systematic review](https://pubmed.ncbi.nlm.nih.gov/39069082/).

**Screen states and FAQs.** Your Progress: empty state “Add a metric or measure an activity to see trends,” sample-free charts until real logs exist, one metric card at a time on mobile, and a detail view for filtering. FAQs: “Why is my consistency different from my progress?” “Does a missing log count as zero?” “Who can see my weight?” “Can I change a measurement?” Monthly recap can highlight a meaningful KPI change only when there is sufficient comparable data and must state the period and unit.

### Checklist time of day and reminder controls

**Checklist layout.** The activity editor adds an optional time-of-day choice: Morning, Afternoon, Evening/Night, or Anytime. Keep current weekday schedule as a separate field. In checklist settings, choose **Grouped by time of day** or **One list**; default to One list for existing users, preserving their current order. If grouped, show accessible section headings, scheduled counts, and the activity's icon; allow reorder within a section and moving between sections. If one list, respect explicit user priority order and display a small time-of-day badge. Completed and pending activities remain visible; time-of-day does not prevent checking off early/late. Today’s earnings and streak logic remain based on the existing scheduled local day, not on these visual sections.

**Notification settings.** Preserve the existing standard morning/evening push schedule and existing enable/disable status on migration. New optional controls: reminder mode (Standard / Custom / Off), per-activity reminder toggle with a selected time, optional extra general check-in, quiet hours, and a per-day delivery preview. A user who chooses Custom can add more than the standard two, but the UI warns about notification fatigue and offers a daily maximum/digest rather than encouraging unlimited alerts. Respect each device's browser/OS permission separately from account preferences; never imply an enabled in-app setting guarantees delivery. Do not auto-enable new reminders when creating or moving an activity. Skip completed activities, deduplicate jobs, respect quiet hours and timezone/DST, and make an activity reminder open its specific activity rather than a generic Home page. W3C guidance favors user control over interruptions; notification permissions still require browser consent. [W3C interruptions](https://www.w3.org/WAI/WCAG21/Understanding/interruptions.html), [MDN Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API).

**Focused UI and FAQs.** Activity editor shows time-of-day as a small segmented choice, then a separate “Remind me” step only if wanted. Checklist header offers Grouped/One list without changing data. Preferences shows a simple Standard/Custom/Off choice; Custom reveals precise controls and “About N alerts on a typical day.” FAQs: “Does Morning mean I must finish before noon?” (No.) “Does changing a section change my reward?” (No.) “Will I get reminders on rest days?” (No.) “Can I mute just one activity?” (Yes.)

### Receipt and statement capture (separate later release)

1. Add “Scan receipt” beside the existing Record purchase action in **Rewards**, using camera capture or file picker. Keep manual entry always available.
2. Validate format/size, strip unnecessary metadata, upload only to a private, owner-scoped temporary location, and show a clear consent/privacy statement before sending it to an OCR provider.
3. Extract merchant, date, currency, total, taxes/tips, and line items when available. Mark confidence/uncertainty and never invent missing fields. A receipt with multiple purchases must allow selecting the reward-relevant line item or entering a custom amount.
4. Prefill the **existing** purchase form. User chooses category/item, reviews amount/date, and presses Save. The existing idempotent purchase/linked-goal operation must perform the actual wallet effect exactly once.
5. Detect likely duplicates (merchant/date/amount plus source hash) and provide “Already recorded?” review; never auto-delete or auto-merge.
6. Show extraction errors, poor-photo retake, currency mismatch, refund/return path, and privacy/delete state. Do not put image bytes or private account numbers into Sheets.
7. Defer bank/credit-card statement photo import until multi-transaction review, redaction, duplicate detection, and sensitive-data retention are designed and tested. No bank login or automatic transaction posting is implied.

### HTML/React structure

- Refactor the large `src/main.tsx` view into focused components (`OnboardingShell`, `ProfileStep`, `CompanionStep`, `ActivityPicker`, `ActivityEditorStep`, `ChecklistReorder`, `ChecklistSections`, `ReminderPreferences`, `GoalPathStep`, `BudgetStep`, `PriorityRankStep`, `GoalEditorStep`, `GoalReview`, `MoneyExplainer`, `ContextFaq`, `CompanionReaction`, `ProgressInsights`, `MetricEditor`, `MetricLogEditor`, `GroupSwitcher`, `GroupSharing`, `TogetherHome`, `GardenView`, `PlantEditor`, `MissionView`, `VersusOptIn`, `ReceiptReview`). Reuse existing task, KPI, purchase, goal, and profile forms/operations instead of duplicating business rules. Do not create a second purchase ledger.
- Use semantic `<main>`, `<nav>`, `<form>`, `<fieldset>/<legend>`, `<label>`, `<button>`, `<details>/<summary>` for FAQs, and a heading hierarchy with one `<h1>` per step. Use `aria-current="step"`, `aria-live="polite"` for status, descriptive controls for sorting, and `role="dialog"`/focus return for overlays. Keep Back/Save/Continue controls consistently positioned.
- Split each screen into a heading/short instruction, one primary card, one primary CTA, and a low-priority FAQ section. On phone, use a single column; on desktop, constrain the setup form to a readable width and optionally place the companion in the free side space. Do not widen a focused form into a dense dashboard.
- Profile dropdown and the renamed sidebar/bottom navigation remain available in ordinary use. During setup, show only safe navigation or a clear Save-and-exit action so accidental tab changes do not discard drafts. All icons have text labels; emojis are decoration, not the sole meaning.

### CSS and design tokens

- Consolidate new styles into component-level stylesheets or CSS modules; avoid adding another unmaintainable global one-line override. Define tokens for forest green, mint, ivory, text, muted text, border, shadow, radii, spacing, font sizes, focus ring, and motion duration. Respect the existing Pronark logo rather than recreating it from the mockup.
- Target comfortable touch controls (about 44 CSS px), readable form labels, consistent 8/16/24 px spacing rhythm, and stable card widths. Use CSS Grid/Flexbox, not absolute positioning for essential form content. Test narrow iPhone width, a wider phone, tablet, and desktop sidebar. Prevent horizontal overflow and ensure on-screen keyboards do not cover Save.
- Separate `goal-target`, `wallet-balance`, `assigned-progress`, and `planned-increase` card styles and labels; do not rely on green color alone to explain money state. Use persistent text under progress bars. FAQs should not dominate the page when collapsed.
- Interaction states: idle, hover, keyboard focus, pressed, loading, saved, validation error, server conflict, empty list, and read-only partner. Provide non-color error text and preserve unsaved input on failed mutations.
- Motion: CSS transitions/keyframes for small button, card, progress, and simple companion loops; limit travel distance and confetti. Use `@media (prefers-reduced-motion: reduce)` to remove nonessential motion. Never let animation block Save or checkoff response.
- Garden CSS: render plant stages as layered illustration/state assets or simple SVG/CSS parts within a stable `aspect-ratio` scene, with accessible text outside the artwork stating current stage and exact progress. A seed can scale gently, leaves can unfold, and the companion can water the plant after server confirmation; avoid continuous high-motion loops, canvas-only critical information, or a fragile animation that rewrites DOM state. Each plant card should have a name, rule summary, participant count, progress, and clear actions; use a responsive grid and a focused plant-detail page rather than an overflowing single garden dashboard. Keep color/shape distinctions for plant stages, not color alone.
- Insights CSS: use clearly differentiated tab/slide headings for Consistency and Your Progress; responsive metric-card grids, legible chart axes/units, text equivalents for trends, and neutral styling for weight/calorie changes. Checklist CSS: use section headings, time badges and comfortable drag targets that work at 320–430 px widths; preserve the one-list view. Notification controls need a compact Standard/Custom/Off choice that does not hide the current standard schedule.

### JavaScript/TypeScript and library choices

- Keep the approved React + TypeScript + Vite + Supabase stack. `package.json` currently contains React, React DOM, Supabase JS, TypeScript, Vite, and Vitest; it does **not** contain drag or animation libraries. Add dependencies only when the specific screen needs them, after bundle/accessibility review.
- For checklist/category ranking, recommend **current `@dnd-kit/react`** (`useSortable`) plus `@dnd-kit/helpers` for moves, with pointer and keyboard sensors. Do not mix the newer package with copied snippets from the legacy `@dnd-kit/core`/`@dnd-kit/sortable` API. Always ship visible Move up/down buttons in addition to drag handles. Persist order as explicit integer positions in an owner-scoped server operation; handle concurrent edits with revision/conflict feedback. [dnd kit React quickstart](https://dndkit.com/react/quickstart/), [sortable state](https://dndkit.com/react/guides/sortable-state-management/), [keyboard/pointer sensors](https://dndkit.com/react/guides/sensors/).
- For screen transitions and mount/unmount of celebration cards, **Motion for React** (`motion`, imported from `motion/react`) is a candidate, particularly `AnimatePresence` and `useReducedMotion`; keep the main mascot poses as lightweight CSS or small original image-state assets. - Implement the companion as a finite state machine or typed event reducer: `idle`, `checkoff-success`, `kpi-hit`, `milestone`, `error/undo`; give events an ID, priority, timeout, and dismiss action. Queue or coalesce simultaneous wins; avoid overlapping popups and duplicate reactions after refresh.

React renders the current stage; CSS or Motion animates only the transition. Keep snapshots for past windows; recalculation after correction updates the current stage and audit entry. Respect `prefers-reduced-motion` and user quiet settings. Lazy-load garden art, keep SVG/image dimensions fixed to avoid layout shift, and do not ship heavy game/physics libraries for simple growth effects.
- Derive Insights KPI summaries through typed aggregation utilities that distinguish totals (steps/miles), averages, latest values (weight), and target attainment; never substitute zero for missing. Use the existing activity KPI data as one source and standalone metric logs as another, with a unified read model but separate ownership. Notification scheduling belongs in the existing worker/job path, not client-side timers; jobs need a unique owner/device-or-channel/date/reminder key, quiet-hour checks, preference revisions, and send-time rechecks of completion and permissions.

A private Supabase Storage bucket can use RLS for owner-scoped files; no public bucket for receipts.
